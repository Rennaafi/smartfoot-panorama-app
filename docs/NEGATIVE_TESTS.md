# Negative tests: what the app does when something goes wrong

Written 2026-11-03, before the first release build.

## The rule

1. An accepted scan is **never lost or corrupted**.
2. The app **never silently writes wrong numbers**: no foot means no measurement, and a strange shape carries a warning.
3. Every failure shows a **plain message that says what to do**.
4. Bonus: the app recovers by itself, without a restart.

Crashes count as failures of rule 3. Destructive tests never run on the real data folder: the automated ones use throwaway temp folders, and the manual ones use `D:\SmartFoot_Test` (set it in Settings, then set it back).

Run the automated tests from `src-tauri/`: `cargo test` (images: `cargo test --test negative_images -- --nocapture` prints the full table).

### Findings from the hands-on run (to fix after the checklist)

- **F1 FIXED 2026-11-03 (uncommitted), SEEN IN THE APP the same day** (room dark, LiDE 300): empty glass = red dots, "Kaki tidak terdeteksi", no blue outline; hand = green, outline follows the fingers, ODD_SHAPE only; packet = green, ODD_SHAPE. Accepting a no-foot scan saves it with the NO_FOOT warning and no measurements (lib.rs accept_scan), so no numbers can be recorded for it. Fix: the "object" must have a mean colour distance of at least 35 from the background, checked inside `analyze::segment`, so the review screen AND the measurement code both get an empty mask (before, measurement had no check of its own and could have recorded numbers for an empty glass). Real LiDE 300 reference scans are in `D:\SmartFoot_RefScans` (7 files, ~34 MB, outside the repo; `cargo test --test reference_scans`): empty glass scored 5-8 inside the "object", hand 122, packet 199, so cutoff 35 sits far from both. Today's three empty scans did not reproduce the green dot with the old code either (Otsu threshold 3-5 against a cutoff of 8); the in-app scan that did was deleted, so the old margin was thin, not absent. Not measured: that the new synthetic fade cases fail on the old code. Cutoff is provisional until real feet on the final casing. A first version of the rule used the Otsu threshold and broke two unit tests: Otsu sits anywhere in the gap of a clean two-group image (10 for a synthetic foot scoring 125), so it is not a contrast measure. Original report:
- **F1 (real bug, medium): empty glass is reported as a foot.** Lid open, nothing on the glass: "Kaki terdeteksi" (green) with a ragged outline. With room light on the outline is the bright patch at the top; in the dark it is the right-hand part of a faint left-to-right brightness gradient. ODD_SHAPE, edge and TWO_OBJECTS warnings fire, but the green dot and the Accept button remain, so measurements could be recorded for no foot. Synthetic A1 missed it because it used flat grey. Proposed fix: minimum-contrast check (object barely different from background = "no foot"); treat edge + odd-shape + second-object together as "no foot". Check real scan numbers before choosing the threshold.
- **STATUS 2026-11-04: F2-F6 are CODED and covered by automated tests where possible (31 tests pass), but NOT yet seen in the app.** F2: outline is drawn only when a foot is found (reference_scans test checks no blue pixels on empty/lid/small-object scans). F3: `scanner::friendly_for` re-reads the device list on "driver threw an exception"; gone = NOT_FOUND, still listed = LOCKED (unit test; the real unplug is still to be re-checked on hardware). F4: finish screen shows a warning when the backup is unreachable or failed. F5: disk-full text ("not enough space", "disk is full", os error 112) maps to a plain Indonesian/English line, in the scanner and everywhere errors are shown. F6: Settings text fields show "✓ Tersimpan" for 2 s, a red error under the field (typed text kept), and Simpan is greyed while unchanged.
- **F2 (cosmetic), partly gone with the F1 fix:** empty glass, the small object and the closed lid now give an empty mask, so no squiggles are drawn for them. Seen in the app for the empty glass: no squiggles.
- **F2 original:** when "no foot found" is shown (lid closed, small object), the finder's blue squiggles are still drawn on the image. Draw no outline when no foot is detected.
- **F3 (real bug, medium): unplugging the USB during a scan shows the LOCK message.** The red box says "kunci transportasi (LOCK) kemungkinan masih tertutup. Buka kunci lalu ulangi" although the cable was pulled and the LOCK was open. Cause (scanner.rs ~line 248): any "driver threw an exception" is mapped to LOCKED. The chip also goes amber "perlu dicek" after replug because of the same mapping. Proposed fix: before choosing the message, re-read the device list; if the scanner is gone, show "Scanner tidak terdeteksi, periksa kabel USB" (NOT_FOUND); only claim LOCK when the scanner is still listed.
- **F4 (small UX):** when the backup drive is missing, the finish screen ("Sesi selesai", green check) says nothing; the warning only shows on the next start screen. Consider showing it on the finish screen too.
- **F5 (wording):** a full disk shows the raw Windows message inside the Indonesian text ("Pemindaian gagal: There is not enough space on the disk."). Map the disk-full error (ERROR_DISK_FULL / "not enough space") to a plain line such as "Disk penuh. Kosongkan ruang atau ganti folder data." Note a scan needs about 35 MB free (26 MB temporary BMP + ~7 MB PNG).
- Room light: with the lid open, light reaching the sensor makes the background bright at the top and confuses the finder. Related to the Stage 2 background/cover decision.

## C. Known limits (not tested, or by design)

- **Null Driver**: Windows installing "Canon LiDE 300 Null Driver" cannot be forced. The code path exists and the detection query works, but it has not been seen end to end since the app was built.
- **Disk full** while a scan is saved, **power cut** during a write: only the parts we can inject (rename/write failures) are tested; B8 and B14 cover the real thing.
- **Odd-shape thresholds** (length 90-420 mm, length/width 1.6-5) are provisional and were tuned on synthetic shapes only. They only warn, never block. Re-tune on real feet in stage 2.
- **Two objects** warning fires when the second object is more than 25% of the foot's area.
- Only the **largest** object is outlined and measured, by design.
- **Seated Cavanagh cutoffs** are not validated; the app records numbers only, no labels.
